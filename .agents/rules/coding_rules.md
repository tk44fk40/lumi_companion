# lumi_companion 開発ルール (Development Rules)

本ドキュメントは「るみぽん！」(`lumi_companion`) の開発およびコード品質、設計指針、モジュール分割、Docstring 記述ルール、準拠コーディング規約を定めたものです。

---

## 1. 準拠コーディング規約
本プロジェクトでは、運用しやすくツール自動化が容易な **「PEP 8 (Python公式スタイル)」** および **「Google Python スタイルガイド (Docstring / 命名規則)」** を基本コーディング規約として採用する。

### 命名規則 (PEP 8)
- **クラス名**: `PascalCase` (例: `LumiApp`, `AppContext`, `AudioProcessorService`)
- **関数・メソッド・変数名**: `snake_case` (例: `extract_frame()`, `subtitle_segments`)
- **定数名**: `UPPER_SNAKE_CASE` (例: `DEFAULT_TIMEOUT_SECONDS`, `MAX_IMAGE_WIDTH_PX`)
- **モジュール・ファイル名**: 小文字の `snake_case` (例: `audio_service.py`, `context.py`)

### 1行長・フォーマット (Ruff / Black 互換) & 日本語改行配慮
- インデント: スペース 4 つ
- 1行の最大長: 88 文字（Ruff 標準）
- **日本語 Docstring / コメントの改行配慮**: リンター (Ruff 等) は全角日本語の表示幅を行長として正確に警告できない場合があるため、日本語の Docstring 詳細文やコメントを記述する際は、読点 (`、`) や句点 (`。`), カンマ (`,`), スペースの位置で意識的に改行を入れ、1行が長くなりすぎないよう配慮する。

## 2. Issue / ブランチ / PR トレーサビリティ & スカッシュマージ規約

作業の開始からマージ・中断・再開まで、全ての変更履歴と進捗状況を完璧に追跡できるよう以下のフローを徹底する。

1. **GitHub Issue の作成とタスクリスト管理**:
   - 新しい作業を開始する際、または区切りの良いタイミングで GitHub Issue を作成する（`gh issue create`）。
   - Issue 本文には、進捗状況をリアルタイムに把握できるよう細分化した**タスクリスト (`- [ ] タスク名`)** を必ず記載し、進捗に応じて更新 (`- [x]`) すること。
2. **Issue 連動ブランチの作成**:
   - 作成した Issue 番号を含む作業用ブランチを作成・チェックアウトする。
   - **ブランチ命名規則**: `issue-<Issue番号>/<簡潔な機能名>` （例: `issue-12/subtitle-queue`）
3. **Pull Request (PR) の作成と Issue 自動クローズ**:
   - 作業完了後、メインブランチ (`master`) に向けて PR を作成する（`gh pr create`）。
   - PR の本文には、マージ時に自動で Issue をクローズさせるため **`Closes #<Issue番号>`** を必ず明記すること。
4. **スカッシュマージ (Squash and Merge) の徹底**:
   - 作業ブランチをメインブランチへマージする際は、コミット履歴を1つに綺麗にまとめるため、必ず**スカッシュマージ (`gh pr merge --squash`)** を行うこと。
5. **計画書 (`implementation_plan.md` 等) へのメタデータ記載**:
   - 計画書を作成・更新する際、ヘッダーに必ず以下のメタデータを記載・追記すること：
     - **関連 Issue**: `#12 (字幕Queueサービスの実装)`
     - **作業ブランチ**: `issue-12/subtitle-queue`
     - **Pull Request**: `#25 (https://github.com/owner/repo/pull/25)`

## 3. モジュール規模制限 & 可読性・シンプルさの重視
- **可読性とシンプルさの最優先**: コードは常に直感的で可読性が高く、シンプルな構成 (KISS原則) を維持する。
- **トリッキー・難解なコードの禁止**: 行数・サイズ制限を回避する目的でワンライナーに詰め込んだり、トリッキーで難解なコードを書くことを厳禁とする。
- **適切なモジュール分割**: 処理が長くなる場合は単一責任の原則 (Single Responsibility Principle) に従い、クラスやモジュールを素直に分割する。
- **行数制限**: 1 ファイルあたりのサイズは **最大 300 行以下**（目標 100〜200 行程度）を厳守する。

---

## 4. Google スタイル Docstring & 日本語コメントの徹底
- すべてのモジュール, クラス, 関数・メソッドに **Google スタイルの Docstring** を日本語で記述する。
- **Docstring 1行目（サマリー行）の規定**:
  - Docstring の 1 行目は **「1行で簡潔な説明タイトル」** とし、1 行目を途中で改行して複数行にすることを禁止する。
  - 補足や詳しい説明を記述する場合は、サマリー行の後に **1 行の空行** を挟んでから詳細本文として記述する（詳細本文内で適切に改行を入れる）。
- 関数・メソッドの Docstring には、以下の項目を明確に記載する:
  - **概要**: 関数の目的と行う処理の概要（サマリー行）
  - **Args**: 各引数の名称, 型, 意味
  - **Returns**: 戻り値の型と意味
  - **Raises**: 発生する可能性のある例外とその発生条件
- コード内には「どのような目的でどういうことをするコードなのか」を簡潔明瞭に日本語インラインコメントで記載する。

## 5. 定数のハードコード禁止 & コンテキスト管理の徹底
- **ハードコードの禁止**: デフォルトのタイムアウト秒数, 画像サイズ(px), デフォルトモデル名, 出力ファイル名, マジックナンバー等の定数値をコード内に直接ハードコードすることを禁止する。
- **コンテキストクラスでの一元管理**: 定数や設定値として使用する数値・文字列・パスは、必ずコンテキストクラス (`AppContext` 等) または設定クラスに定義し、コンテキスト経由で参照・使用する。

---

## 6. シンプルな例外処理の徹底
- **例外ブロックのシンプル化**: `try-except` ブロック内の処理は極力単純にし、例外発生時のログ記録（`logger.error` やエラーメッセージ設定等）にとどめる。
- **エラー処理の分離**: 複雑なリカバリロジックやフォールバック処理は `except` ブロック内でネストさせず、例外ブロックを抜けてから行うか、独立したハンドラーで処理する。

---

## 7. 設計原則 & 推奨デザインパターン
本プロジェクトでは、コードの可読性・拡張性・リアルタイム性・テスト容易性を高めるため、以下の 4 大デザインパターンを基本原則として採用する。

1. **Strategy パターン ＋ DI (依存性注入)**:
   - LLM推論, 音声VAD, 画像抽出等のプロバイダー処理は `typing.Protocol` で抽象化し、コンストラクタ経由で注入すること (`pytest` でのモック差し替えを容易にする)。
2. **Facade パターン (オーケストレーター)**:
   - `LumiApp` 等のメイン処理は複雑なサブシステム群を統合するファサードとして機能させ、外部や呼び出し元へはシンプルな単一インターフェースのみを公開すること。
3. **Context / State パターン (状態一元管理)**:
   - 字幕履歴、キャプチャ画像、アプリ設定などの状態データは `AppContext` 等の専用クラスにカプセル化し、各サービス間で直接状態を散らかさないこと。
4. **Producer-Consumer (生産者・消費者) パターン (非同期Queue)**:
   - 音声VAD/字幕抽出や画面キャプチャ（生産者）と、LLM推論/応答生成（消費者）の間に `asyncio.Queue` 等の緩衝キューを挟むこと。
   - 生成周波数と消費（推論）速度の差異を非同期で吸収し、メインイベントループやデータキャプチャ処理を一切ブロッキングしない設計とすること。

---

## 8. コード品質 & 自動化ツールへの適合（AIへの要求事項）
- Python 3.12 準拠。すべての関数・メソッド・クラスに明確な型注釈 (Type Hints) を付与すること。
- **静的型チェック**: `uv run basedpyright` を全件エラー0で通過する型安全なコードを生成すること。
- **コードフォーマット・Linter**: `uv run ruff check --fix .` および `uv run ruff format .` の規約（ダブルクォート、4スペースインデント、E501除外等）に完全適合するコードを出力すること。

---

## 9. 非同期 (Asyncio) イベントループのブロッキング禁止
- Whisper音声認識推論、VAD推論、OpenCVによる画像取得・リサイズなどの重いCPU/GPU処理は、メインの `asyncio` イベントループ上で直接実行しない。
- 必ず `asyncio.to_thread` や `loop.run_in_executor` を使用してバックグラウンドスレッドに委譲し、イベントループのブロッキングを防ぐ。

---

## 10. 非破壊デバッグ・成果物の透明性
- 各コンポーネント処理の中間出力（字幕JSON, 字幕SRT, 抽出画像, Ollamaペイロード等）は `debug_output/` ディレクトリへ非破壊的に出力可能とする。
- パイプライン全体を実行せずとも、単体コンポーネント（Step 1〜4等）の独立デバッグが実行できるようにスクリプト化する。

---

## 11. AIエージェントの自律コード生成 & セルフチェック規範
AIエージェントは、本プロジェクトでコードの作成・修正・リファクタリングを行う際、以下の行動規範を遵守すること。

1. **インターフェース（シグネチャ・型）の優先提示と合意**:
   - 新しい関数・クラスの作成や重要なリファクタリングを行う際、いきなり内部実装コードを出力しないこと。
   - まず**関数のシグネチャ（関数名、引数の型、戻り値の型）および Google スタイル Docstring のみの骨組み（スタブ）**を提示し、型定義の合意を得てから実装に進むこと。
2. **TDD (テスト先行提案) の自律実行**:
   - インターフェース合意後、実装コードを書く前に原則としてまず `tests/` ディレクトリに該当する単体テスト（`pytest`）を作成・提示し、その後にテストを全件パスする実装コードを生成すること。
3. **小単位（アトミック）生成とファイル行数制限の徹底**:
   - 1回の応答で変更・提案する範囲は最小限（1〜2ファイル、多くても50〜100行程度）に留め、一度に肥大化したコードを一括生成しないこと。
   - Section 3 に定めた「1ファイル最大300行以下」を厳守し、ファイルが巨大化する場合は自発的にモジュール分割を提案・実行すること。
4. **作成コードの「適切さ・妥当性」に関する自律セルフチェック**:
   - `ruff` や `basedpyright` などのツールチェック・テスト合格は当然の前提条件とし、コードを出力する前に**「自身が作成したコードが本当に適切か」**を以下の観点で自己検証（セルフチェック）すること：
     - **① 開発ルール (`coding_rules.md`) への完全適合性**: 本ドキュメントの全条項（GoogleスタイルDocstring規約、1ファイル最大300行制限、ハードコード禁止と `AppContext` 管理、推奨デザインパターン等）を漏れなく遵守しているか？
     - **② 要件適合性**: 依頼された目的・課題を過不足なく解決しているか？（余計な実装や的外れな処理がないか）
     - **③ 設計整合性**: プロジェクトの既存アーキテクチャ（DI構造、Facade構成、Producer-Consumerパターン等）に反していないか？
     - **④ 簡潔性 (KISS原則)**: 不要なクラス化や過剰な抽象化（Over-engineering）をせず、最もシンプルで可読性の高い記述になっているか？
     - **⑤ 副作用と影響範囲**: 既存の他コンポーネントや呼び出し元へ意図しない破壊的影響（副作用）を与えていないか？
     - **⑥ 実行パフォーマンス**: 重い処理で `asyncio` イベントループをブロックする記述が含まれていないか？
    - **【必須】セルフチェック結果の報告義務**:
      コード修正・作成・リファクタリング等の作業完了時には、上記の観点で自ら点検した結果を簡潔（箇条書き等）に整理し、**必ずユーザーへの回答末尾に付与して報告**すること。

## 12. テストコード (`tests/`) のモジュール分割 & 品質妥当性規範
テストコードはプロダクションコードと同等以上の品質・可読性・構造化を維持すること。

1. **適切なモジュール・機能分割**:
   - 1つのテストファイルに多数の異なる機能テストを無秩序に詰め込まないこと。
   - テスト対象のモジュール・機能単位（例: `test_ollama.py`, `test_extractor.py` 等）で `tests/test_*.py` に適切に分割し、1ファイルあたりの規模を短くシンプルに保つこと。
   - 共通の初期化処理やモック定義は `conftest.py` やテストヘルパーに分離し、テストファイルの肥大化を防ぐこと。
2. **テスト目的とアサートの妥当性**:
   - 何を検証するためのテストかがテスト関数名および Docstring で明確であること。
   - 単に例外が発生しないことの確認にとどまらず、期待する戻り値や状態変化が正しくアサート (`assert`) されていること。
3. **AAA (Arrange-Act-Assert) パターンの徹底**:
   - テスト処理を「準備 (Arrange) ➔ 実行 (Act) ➔ 検証 (Assert)」の明確な3段構造とし、第三者が直感的に理解できるように記述すること。
4. **シンプルさと非肥大化 (トリッキーなコードの禁止)**:
   - テストコード内で複雑な条件分岐 (`if`) や動的ループ (`for`) を記述しないこと（テストコード自体のバグを防ぐため）。
   - 不必要な過剰モック（Over-mocking）を避け、可能な限りデータクラスや設定の実物オブジェクトを活用すること。
5. **テストカバレッジ・モック化ナレッジの参照と継続メンテ**:
   - 単体テストにおける未カバー（モック化）許容指針およびモジュールごとの技術的根拠は [docs/TEST_COVERAGE_KNOWLEDGE.md](file:///home/tk44/ghq/github.com/tk44fk40/lumi_companion/docs/TEST_COVERAGE_KNOWLEDGE.md) で一元管理し、テスト設計時に常に参照すること。
   - 新しいモジュール追加やリファクタリング、外部依存の変更時には同ナレッジドキュメントを同時に更新・メンテナンスすること。
