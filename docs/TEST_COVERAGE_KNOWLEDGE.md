# テストカバレッジ・モック化設計ナレッジ (Test Coverage Knowledge)

本ドキュメントは `lumi_companion` における単体テスト（pytest）のカバレッジ方針、未カバーを許容する厳格な技術的指針、および各モジュールのテスト網羅状態を一元管理するナレッジドキュメントです。

---

## 1. カバレッジ基本方針
- **ビジネスロジック・データモデル・例外処理 (異常系)・クライアント/抽出ロジック**: 原則 **100%** のテスト網羅を行う。
- **生通信・重い外部バイナリ**: 外部サーバーや特定GPUハードウェアへの直接依存を排除するためモックトランスポート (`httpx.MockTransport` / `unittest.mock`) やダミーデータを用い、**クライアント/ハンドラー自体の全分岐・全例外処理ロジックは 100% 単体テストで網羅**する。

---

## 2. 単体テストで「未カバーにしてよい」真の許容指針

1. **実行環境差異による排他的な分岐（ハードウェア/OS依存のフォールバック）**
   - **具体例**: `config.py` における GPU (CUDA) 搭載環境と非搭載環境のライブラリパス自動探索。
   - **理由**: 単一の実行環境（非GPU環境のCIやローカルCPU環境など）では物理的にどちらか一方の分岐しか通過しないため。
2. **エントリーポイントのボイラープレート**
   - **具体例**: `if __name__ == "__main__": asyncio.run(main())` の起動構文。

## 4. 未カバー箇所の詳細と技術的根拠

#### 設定モジュール (`src/lumi_companion/config.py`)
- **未カバー行**: L31-32, 35, 53, 58-59, 61-62 (計 8 行)
- **技術的根拠**:
  - `_find_cuda_libraries()` 内で、システムに NVIDIA GPU/CUDA ツールキットが存在する場合と存在しない場合で分岐する。
  - テスト実行環境が CPU/非GPU 環境の場合、CUDA 探索パスの環境変数追加ブロックは通過しないため未カバーとなる。これは環境依存の正常な設計挙動である。

## 5. 今後のコード改修・リファクタリング時のメンテナビリティ指針
- 新しいモジュールや外部クライアントを追加する際は、単にサービス層でモック化するだけでなく、クライアントクラス自体の通信ロジック・エラーハンドリングをモックトランスポートを用いて 100% 単体テストすること。
- 新たな異常系処理を追加した場合は、必ず対応するテストケースを `tests/` に追加し、全体カバレッジ 98% 以上を維持すること。
