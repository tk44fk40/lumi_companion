# lumi_companion 開発・レビュー標準チェックリスト雛形

本ドキュメントは、新規機能実装・リファクタリング・バグ修正時に計画書 (`implementation_plan.md`) や PR レビューで利用する標準チェックリストの雛形です。

---

## 開発時・自律セルフチェックリスト雛形

```markdown
## 開発時・自律セルフチェックリスト

### 1. 設計・規模・可読性
- [ ] **モジュール規模**: 新規・修正モジュールともに目標 200 行以内（最大 300 行以下）を厳守しているか。
- [ ] **KISS原則 & 簡潔性**: 難解・トリッキーな処理を排除し、シンプルで直感的な実装になっているか。
- [ ] **重複排除**: 既存機能との重複がなく、責務（単一責任原則: SRP）が明確に分離されているか。
- [ ] **定数・設定一元管理**: コード内でのマジックナンバーや固定文字列の直書きを排除し、`AppContext` / `Settings` から注入しているか。
- [ ] **適切なコメント**: 処理の「目的」と「目的のためにどうしているか」を明確にコメント・Docstring で説明しているか。

### 2. コード品質・型安全性・Docstring
- [ ] **完全な型注釈**: 新規・修正した全関数・クラスに厳格な型アノテーションが付与されているか（`Any` 排除、具体型 / `Self` を使用）。
- [ ] **Google スタイル Docstring**: 全関数・クラスに日本語 Docstring（概要, `Args`, `Returns`, `Raises`）が記述されているか。
- [ ] **静的解析**: `uv run basedpyright` を実行し、エラー 0 件であることを確認したか。
- [ ] **フォーマット & Lint**: `uv run ruff check .` および `uv run ruff format .` でスタイル違反がないことを確認したか。

### 3. テスト品質・網羅性 & 検証
- [ ] **妥当な検証**: テスト対象機能について本質的かつ妥当な検証を行っているか。
- [ ] **テスト漏れ・エッジケース**: 空配列、1件のみ、極小ギャップ、重なり合っている場合などの境界値テストが漏れなく網羅されているか。
- [ ] **カバレッジ確認**: 未カバー箇所が発生していないか、また未カバー箇所がある場合はその理由が妥当か。
- [ ] **AAA パターン**: Arrange-Act-Assert 構造で読みやすく保守性の高いテストになっているか（テスト内に複雑な `if`/`for` を書かない）。
- [ ] **回帰テスト**: `uv run pytest` を実行し、既存テストおよび新規テストが全てパスすることを確認したか。
- [ ] **非破壊デバッグ検証**: 対象のデバッグスクリプト等を実行し、出力結果（SRT/JSON/画像等）に期待通りの補正が反映されていることを確認したか。
```

---

## チェックリスト運用ルール

1. **計画書への組み込み**:
   - すべての機能実装・修正計画書 (`implementation_plan.md`) に本チェックリストを組み込み、進捗と合致させてチェックを完了させる。
2. **自律的チェック＆修正ループ**:
   - 実装中および完了時に上記観点ですべてセルフチェックを行い、問題がなくなるまで自律的に修正を繰り返してからユーザーへ完了報告する。
